# RAFIQ (رفيق) — AI Safety Companion for Hajj & Umrah Pilgrims

An autonomous AI safety agent for pilgrim protection during mass gatherings (Hajj/Umrah),
built for the GSMA Open Gateway MENA Ignite Hackathon. Rafiq uses real Google Gemini
function-calling to decide, live and unscripted, when to call Nokia CAMARA network
APIs — Location Verification, Quality on Demand (5G priority), Carrier SMS, and
Device Status — during a natural-language conversation with a pilgrim in distress.

This is not a rules engine with an AI-sounding wrapper: every emergency response is
generated by the model after it has already seen real tool results, and the same
telecom API layer is shared live between the pilgrim-facing app and the authority-side
Security Command Center dashboard.

## Core Features

**Pilgrim Companion (pilgrim-facing chat)**
- Multimodal input: text, image, and voice — the AI agent decides which Nokia tools to
  call based on the actual content of the message, not keyword matching.
- **Self-emergency SOS (full tier):** on detecting genuine distress about the pilgrim
  themself, the agent autonomously calls the Location, QoD (5G priority boost), and
  Carrier SMS APIs, and logs the incident with the Command Center.
- **Companion assistance (lower tier):** on detecting that someone ELSE (a companion,
  friend, or family member) needs help, the agent logs a registry-only incident with
  the Command Center — deliberately without sending SMS or boosting network priority,
  since that tier is not about the reporting pilgrim's own safety. This distinction is
  handled by the model's own reasoning, not a keyword rule.
- Ritual/fiqh Q&A (Tawaf, Sa'i, Ihram, etc.) in English or Arabic.
- In-session conversational memory (facts mentioned earlier in the chat are recalled
  later in the same session).
- A visible, per-step AI reasoning trace (tool called, why, arguments, and real result)
  for transparency during judging.
- A manual "Report Companion Needs Help" form and a manual Emergency SOS button, both
  independent of the AI pipeline, so a pilgrim always has a path to safety even if the
  AI service is temporarily unavailable.

**Security Command Center (authority-facing dashboard)**
- Live, auto-refreshing incident feed shared with the pilgrim-side app via the same
  in-memory Nokia client state.
- Incident cards clearly badged `SELF SOS` vs `COMPANION REPORT`, with the actual
  subject of concern (e.g. "Pilgrim's brother — Mohamed") always shown.
- **AI dispatcher briefings:** a short, plain-language summary generated per incident
  from the raw data, so a responder can act in seconds.
- **AI severity triage:** ranks all active incidents by urgency (medical risk,
  incident type, reported severity) with a rationale.
- **Zone-clustering alert:** real aggregation over live incident data — flags a zone
  once 2+ active incidents are logged there, as an early mass-incident indicator.
- **Zone summary panel:** pilgrim and incident counts per predefined Masjid al-Haram zone.
- A simulated, clearly-labeled weather widget (explicitly marked DEMO DATA — this
  build has no live weather feed).
- A clearly labeled "Simulate Test Incident" demo tool for testing/judging, separate
  from the real AI-triggered incident path.

## Setup

### 1. Requirements
- Python 3.10+
- A Google Gemini API key (free tier is sufficient — see Google AI Studio)

### 2. Install dependencies
```bash
pip install -r requirements.txt
```

### 3. Configure environment variables
Create a `.env` file in the project root with:
```
GEMINI_API_KEY="type your key"
GEMINI_MODEL=gemini-3.6-flash
```
- `GEMINI_API_KEY` is **required**. Without it, the app still runs, but the AI agent
  returns a graceful "AI temporarily unavailable" message (in the pilgrim's selected
  language) and points the user to the manual SOS button instead of crashing.
- `GEMINI_MODEL` is **optional**. If omitted, the agent tries a built-in list of
  Gemini Flash models in order and falls back automatically only on genuine API
  errors (not on slow-but-successful responses).
- A `NOKIA_API_KEY` variable may appear in older `.env` files from earlier project
  iterations — it is **not read anywhere in the current code**. The Nokia CAMARA
  layer in this build is a fully simulated client (see Limitations below), so no
  real Nokia credentials are required to run or judge this submission.

### 4. Run the app
```bash
streamlit run app.py
```
The app opens in your browser, typically at `http://localhost:8501`. The Pilgrim
Companion tab is open by default; the Command Center tab requires a security
passcode (set inside `app.py`) to unlock — this is intentional, simulating
authority-only access.

## Instructions to Run (for hackathon reviewers)

1. Install dependencies: `pip install -r requirements.txt`
2. Add a `.env` file with at least `GEMINI_API_KEY=<your key>` (see Setup above).
3. Run: `streamlit run app.py`
4. On the **Pilgrim Companion** tab: fill in a pilgrim name/phone in the sidebar,
   then type a message like *"I feel dizzy near the Clock Tower"* into the chat to
   see the AI agent autonomously call the Nokia tools and respond. Try *"my brother
   is injured"* afterward to see the lower-tier companion-assistance path.
5. Switch to the **Command Center** tab, enter the passcode, and see the incident(s)
   just created — including the AI dispatcher briefing and the "Run AI Triage" button.
6. Optional: use the sidebar's manual SOS / companion-report buttons, or the Command
   Center's "Simulate Test Incident" demo tool, to test without the AI in the loop.

## Testing

This submission includes 7 automated test files (`test_*.py`), covering:
- Core agent logic: conversation memory, model-fallback behavior, reasoning trace
  content, and the third-party-distress prompt handling (`test_agent_core.py`)
- The two-tier SOS system: confirming the companion-assistance tier never sends SMS
  or boosts QoS, and that resolving one tier never affects the other
  (`test_companion_assistance.py`, `test_manual_companion_form.py`)
- Real Streamlit UI behavior via Streamlit's official AppTest framework, including a
  regression test for a since-fixed infinite-loop bug in multimodal (image/voice)
  input handling (`test_app_ui.py`, `test_stress_loop.py`)
- Command Center features: incident badges, zone clustering, zone summary, and AI
  briefing/triage fallback behavior (`test_command_center.py`)
- Graceful failure handling: confirms the pilgrim never sees a raw error/exception
  string, in either English or Arabic, even under a genuine (not mocked) API failure
  (`test_graceful_failure.py`)

Run any individual suite with:
```bash
python3 test_agent_core.py
```

## Known Limitations (disclosed for transparency)

- **Nokia CAMARA APIs are simulated**, not live network calls. `nokia_client.py`
  implements realistic request/response shapes for Location Verification, QoD, SMS,
  and Device Status, but `get_device_status` always returns `CONNECTED` — there is no
  real connectivity signal in this build, so "device reachability" should be read as
  illustrative, not measured.
- **Weather data is simulated and clearly labeled as DEMO DATA** in the UI — there is
  no live weather integration.
- **In-memory, single-process state.** Shared data (incidents, QoS status, locations)
  lives in RAM via Streamlit's `@st.cache_resource` and is shared across all sessions
  connected to one running server process — this is what lets the Pilgrim Companion
  and Command Center interact live, but it means a server restart clears all data, and
  this build has not been load-tested beyond small-scale demo use (a handful of
  concurrent sessions). Production deployment would need a real database/cache layer
  (e.g. Redis or Postgres) for durability and horizontal scaling.
- **AI features degrade gracefully but are not free of the model's own limits.** If
  the Gemini API is rate-limited or unreachable, the pilgrim-facing chat and the
  Command Center's dispatcher briefing/triage both fall back to clearly-labeled,
  deterministic (non-AI) behavior rather than failing silently or showing raw errors.

## Architecture Summary

- **AI/Agent layer:** Google Gemini (Flash) via the `google-genai` SDK, using native
  function calling in a hand-written multi-turn agentic loop (model → tool → model),
  per the Resource & Tooling Guide's definition of "agentic": each CAMARA API is a
  tool the agent decides when to call, not a button the user presses.
- **Telecom data layer:** Nokia CAMARA-aligned APIs (Location Verification, QoD, SMS,
  Device Status), simulated via `nokia_client.py`.
- **Frontend:** Streamlit, with shared global state (via `@st.cache_resource`) linking
  the pilgrim-facing app and the authority-facing Command Center in real time.
